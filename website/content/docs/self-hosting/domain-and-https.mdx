---
title: Domain, IP and HTTPS
description: Point Workspace at a domain with automatic HTTPS, run it on a bare IP address, or put it behind a proxy you already have.
---

Workspace is served at one address, `APP_URL`, which the installer builds from what you give it. Pick the case that
matches your server.

| You have | Use | Address people open |
|---|---|---|
| A domain or subdomain | HTTPS with a free Let's Encrypt certificate (recommended) | `https://work.example.com` |
| Only the server's IP (a trial, an internal network) | Plain HTTP | `http://203.0.113.10` |
| A load balancer, a tunnel or your own nginx | TLS ends in front of Workspace | whatever your proxy serves |

## With your own domain

<Steps>
<Step>

### Point the name at the server

At your DNS provider, add a record for the name people will open, usually a subdomain:

| Type | Name | Value |
|---|---|---|
| `A` | `work` | the server's public IPv4, e.g. `203.0.113.10` |
| `AAAA` (optional) | `work` | the server's IPv6 |

Check it before installing: `dig +short work.example.com` must print the server's IP.

</Step>
<Step>

### Open ports 80 and 443

Let's Encrypt verifies the domain over port 80 and people connect on 443. Allow both in the server's firewall and
in your cloud provider's security group.

</Step>
<Step>

### Install with that name

Give the installer the domain and an e-mail for certificate notices. Caddy obtains the certificate on first start
and renews it on its own; the installer prints `https://work.example.com/setup`.

</Step>
</Steps>

<Callout type="info">
  Behind Cloudflare, leave the record as *DNS only* (grey cloud) until the certificate is issued. After that you can
  turn the proxy on with SSL mode **Full (strict)**.
</Callout>

Extra names are optional and each needs its own DNS record: `FILES_DOMAIN` for the bundled S3 storage,
`MEET_DOMAIN` for video meetings, `API_DOMAIN` for API-key integrations.

## On other ports

Ports 80 and 443 (where people connect) and 3000 and 4000 (the app's direct web and API ports, on `BIND_ADDRESS`)
may already belong to another program on the server. The installer checks: for each port in use it asks for
another one (with `--non-interactive` it takes the next free one) and writes the choice into `.env`.

| Setting | Default | What it is |
|---|---|---|
| `HTTP_PORT` | 80 | Plain HTTP through Caddy, and Let's Encrypt's check |
| `HTTPS_PORT` | 443 | HTTPS through Caddy |
| `WEB_HOST_PORT` | 3000 | The web app, directly (your own proxy, or a quick look on the server) |
| `API_HOST_PORT` | 4000 | The server's API, directly |

Choose them up front:

```bash
curl -fsSL https://raw.githubusercontent.com/hungga1711/workspace/main/infra/production/install.sh | HTTP_PORT=8080 WEB_HOST_PORT=3100 sh
# or later: set them in .env, then
docker compose up -d
```

Another HTTP or HTTPS port becomes part of the address (`http://203.0.113.10:8080`). Let's Encrypt still needs 80 and
443 reachable from the internet, so with a domain on other ports either terminate HTTPS in your own proxy and set
`TLS=off`, or use your own certificate (below).

## With only an IP address

Let's Encrypt in this setup issues certificates for domain names, so on a bare IP Workspace runs over plain HTTP:

```bash
TLS=off ./install.sh --non-interactive --app-domain 203.0.113.10
# APP_URL becomes http://203.0.113.10; add HTTP_PORT=8080 for another port
```

Browsers allow less on plain HTTP. What you lose until you move to a domain:

| Needs HTTPS | Without it |
|---|---|
| Video meetings and calls (camera and microphone) | Agenda, minutes and action items still work |
| Browser push notifications | In-app notifications still work |
| Installing Workspace as an app (PWA) | Use it in the browser |

Sign-in cookies are sent without the `Secure` flag on HTTP, so keep an IP-only installation on a network you trust.

## The bundled Caddy

Caddy serves the names in `.env` and routes them:

| Public | Goes to |
|---|---|
| `https://APP_DOMAIN/*` | web app `app:3000` |
| `/socket.io/*`, `/storage/*`, `/api/mcp`, `/api/docs` on the app domain | server `app:4000` |
| `https://FILES_DOMAIN` (`--profile s3`) | S3 `s3:8333` |
| `https://MEET_DOMAIN` (optional) | LiveKit `livekit:7880` |
| `https://API_DOMAIN` (optional) | server `app:4000` |

Certificates, one of:

- **Let's Encrypt** (default): automatic over ports 80 and 443, renewed before expiry.
- **Your own certificate**: add `tls /certs/fullchain.pem /certs/privkey.pem` to the site in `caddy/Caddyfile` and
  mount the files at `/certs`.
- **TLS ends in front** (load balancer, Cloudflare Tunnel): `TLS=off`, and Caddy serves plain HTTP on port 80.

### Why Caddy, not nginx

The stack used nginx with a separate certbot container until
[ADR-0021](https://github.com/hungga1711/workspace/blob/main/docs/adr/0021-one-server-no-valkey.md). The goal was
the fewest moving parts for one person running one server:

| | Caddy (now) | nginx + certbot (before) |
|---|---|---|
| HTTPS certificates | Obtained and renewed by Caddy itself | A second container, a renewal schedule and a reload |
| Configuration | One short `Caddyfile`; a site is its domain name | Server blocks, TLS settings and redirects by hand |
| WebSocket, HTTP/2, HTTP/3 | On by default | Configured per location |
| Containers to run and update | 1 | 2 |

Nothing in Workspace depends on Caddy; keep your own proxy if you have one.

## Your own proxy

Run without Caddy: `docker compose up -d --scale caddy=0`. The app then listens on `BIND_ADDRESS` (default
`127.0.0.1`): web 3000, server 4000, S3 8333, LiveKit 7880. Route as in the table above. Any proxy must:

- upgrade WebSockets on `/socket.io/`;
- keep the original `Host` on the files domain (S3 signatures include it);
- set `X-Forwarded-For` and `X-Forwarded-Proto`;
- allow large bodies on `/storage/` and the files domain.

With more than one proxy in front, set `TRUSTED_PROXY_HOPS`. A complete host nginx configuration is in
[infra/production/README.md §5](https://github.com/hungga1711/workspace/blob/main/infra/production/README.md#5-https--reverse-proxy).

## Moving to another address later

Run the installer again with the new name: it keeps `.env` and every secret and rewrites only `APP_DOMAIN`,
`APP_URL` and the TLS setting. By hand, edit those in `infra/production/.env`, then `docker compose up -d`.

After a change of address, people sign in again and each person reconnects the browser extension (its code contains
the server address).
