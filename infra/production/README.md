# Running workspace on your own server

> **Status (1.0.0).** Verified end to end on a Docker host: a plain `docker compose up -d` without `.env`,
> `install.sh` (also over a stack started that way), setup, invitations with a temporary password, chat with files
> on local disk, live updates over WebSocket, search, a container restart (everyone stays signed in) and HTTPS
> through Caddy. Not yet verified on this release: a real Let's Encrypt issuance on a public domain, video meetings
> (LiveKit), Web Push, and `backup.sh`, `restore.sh` and `upgrade.sh` since the backend became one process
> ([ADR-0021](../../docs/adr/0021-one-server-no-valkey.md)). Please report rough edges.

One server, Docker Compose. Everything (database, search, sign-in, file storage, the backend and the web app)
runs from `infra/production/docker-compose.yml`. One installation holds one company workspace, created on first
visit at `/setup`.

**In five minutes** (a Linux server with Docker, DNS of your domain pointing at it):

```bash
curl -fsSL https://raw.githubusercontent.com/hungga1711/workspace/main/infra/production/install.sh | sh
# or, from a checkout: infra/production/install.sh
```

It asks for the domain, an optional second domain for S3 file storage (empty: files on this server's disk), an
e-mail for Let's Encrypt and an optional SMTP server, generates every secret into `.env`, starts the stack and prints the `/setup` address with
the setup token. `--non-interactive --app-domain … --files-domain … --email …` for scripts; running it again keeps
`.env` and its secrets. Just trying it on your laptop: `docker compose up -d` in this directory, without any `.env`,
serves `http://localhost` (secrets are generated by the `init` job). Platforms with their own deploy flow (Coolify,
Portainer, CasaOS, Unraid, Railway): [`infra/templates/`](../templates/README.md).

## 1. Requirements

| | Minimum | Recommended |
|---|---|---|
| CPU | 1 vCPU | 2 vCPU |
| RAM | 1 GB | 2 GB |
| Disk | 20 GB SSD | 50 GB+ SSD (files grow with use) |

Three containers run by default: `postgres`, `app` and `caddy`. A fresh installation idles at about 300 MB (`app`
200 MB, Postgres 80 MB, Caddy 15 MB); Postgres grows with data and load. The image is ~290 MB. Building
the image needs ~2 GB of free RAM and ~5 GB free disk (the build skips type checking and lint, which CI runs; on a
smaller server pull the prebuilt image, or build elsewhere and `docker save | docker load` it). How many people a
given server carries at once: see [§10 Capacity](#10-capacity).

- Linux (x86_64 or arm64) with Docker Engine 24+ and the Compose plugin v2.24+.
- A domain with a DNS record pointing at the server, e.g. `work.example.com`. Add `files.` (bundled S3 storage),
  `meet.` and `api.` later if you need them (`FILES_DOMAIN`, `MEET_DOMAIN`, `API_DOMAIN`).
- Ports 80 and 443 open (plus TCP 7881 and UDP 50000–50100 for video meetings).
- An SMTP account for outgoing e-mail (invitations, password reset); optional, see the table.

What runs, and what you can leave out:

| Service (compose name) | Required? | Without it |
|---|---|---|
| PostgreSQL (`postgres`) | required | nothing starts |
| The app (`app`): web app + backend server | required | (runs migrations on every start, then both processes) |
| Caddy (`caddy`) | required unless you bring your own proxy (§5) | no HTTPS, no single public address |
| File storage | required, local disk by default | files live in the `data` volume, served by the server at `APP_URL/storage/` with signed, expiring links |
| S3 storage (`--profile s3`, bundled SeaweedFS on `FILES_DOMAIN`; or your own S3/R2 via `S3_ENDPOINT`) | optional | files on local disk instead; LiveKit meeting recordings need S3 |
| SMTP (`SMTP_URL`, `MAIL_FROM`) | optional | no invitation and password-reset e-mails (admins copy the activation link from Admin › Members instead), no daily digest |
| AI: a provider connected in Admin › AI (or `*_API_KEY`) | optional, off by default | Admin › AI has two switches (the company's assistant; recording staff use of ChatGPT/Claude/Gemini/Copilot through the extension). Both off: no AI anywhere |
| Web Push (`VAPID_*`, a build argument) | optional | no browser push; in-app notifications work |
| LiveKit (`--profile meet`) | optional | no video meetings or calls; agenda, minutes and action items work |
| PgBouncer (`--profile pgbouncer`) | optional | direct Postgres connections |

## 2. Configure

`install.sh` does this for you. By hand:

```bash
git clone <repository url> workspace && cd workspace/infra/production   # or download and unpack a release archive
cp .env.example .env
for v in INTERNAL_TOKEN_SECRET SESSION_SECRET AUTH_SECRET POSTGRES_PASSWORD PG_OWNER_PASSWORD PG_APP_PASSWORD \
         S3_ACCESS_KEY_ID S3_SECRET_ACCESS_KEY; do
  sed -i "s|^$v=.*|$v=$(openssl rand -hex 32)|" .env
done
nano .env   # APP_URL, APP_DOMAIN, LETSENCRYPT_EMAIL, COMPOSE_PROFILES; S3_ENDPOINT/FILES_DOMAIN for S3; SMTP_URL, MAIL_FROM
chmod 600 .env
```

A secret left empty is generated once by the `init` job into the `secrets` volume instead; a value in `.env` always
wins. Keep `.env` and that volume safe and backed up (`backup.sh` saves both): the Postgres passwords are written
into the database on its first start. `COMPOSE_PROFILES` in `.env` lists the optional parts that start with a plain
`docker compose up -d` (`s3`, `meet`, `pgbouncer`).

E-mail is optional. Without `SMTP_URL` nothing is sent: Admin › Members hands over activation links and
temporary passwords for you to pass on (chat, in person), password reset by e-mail is unavailable (an admin
sets a temporary password instead) and the daily digest is off. Add the relay later without rebuilding.
`SMTP_URL` is the company's own mail server or relay, e.g. `smtp://user:password@smtp.example.com:587`
(`smtps://…:465` for implicit TLS; URL-encode special characters in the password). To check it, invite an address
at [yopmail.com](https://yopmail.com) (a public, throwaway inbox) and open that inbox.

## 3. Start

```bash
# Either use the prebuilt image CI publishes (recommended on small servers: no build, no 2 GB of build RAM)…
WORKSPACE_IMAGE=ghcr.io/hungga1711/workspace:1.0.0 docker compose pull     # or put WORKSPACE_IMAGE in .env
# …or build it from the repository (~5–10 min)
docker compose build
docker compose up -d                       # Caddy obtains the Let's Encrypt certificate by itself (see 5)
docker compose ps                         # wait until app is "healthy"
```

Start order is handled by health checks: secrets (`init`) → Postgres → `app` (migrations, then the server and the
web app) → Caddy. Caddy asks Let's Encrypt for the certificate as soon as DNS points here and port 80 answers;
until then HTTPS requests fail. Every long-running container has `restart: unless-stopped`; if either process in
`app` stops, the container stops and is restarted.

## 4. First run

Open `APP_URL` (e.g. `https://work.example.com`). With no workspace yet you land on **/setup**: enter
the company name, the owner's name, e-mail and password, and the **setup token**. The token keeps anyone
who reaches the server before you from becoming its owner: it is `SETUP_TOKEN` from `.env`, or, when that is
empty, generated at the first start and printed by `docker compose logs app | grep "setup token"` (it is also
kept in the `data` volume as `/data/setup-token`). Setup creates the workspace and signs the owner in;
`/setup` is closed from then on. Invite everyone else from Admin → Members: with SMTP they get an e-mail,
without it you copy each activation link from the same screen.

## 5. HTTPS / reverse proxy

**Bundled Caddy** (service `caddy`, config in `infra/production/caddy/`) serves the names in `.env`:

| Public | Internal |
|---|---|
| `https://work.example.com/*` (`APP_DOMAIN`) | `app:3000` (the web app) |
| `https://work.example.com/socket.io/*`, `/storage/*`, `/api/mcp`, `/api/docs` | `app:4000` (the server: Socket.IO over WebSocket only, local disk storage, MCP, API docs) |
| `https://files.example.com` (`FILES_DOMAIN`, `--profile s3`) | `s3:8333` (presigned uploads/downloads, `Host` kept) |
| `https://meet.example.com` (`MEET_DOMAIN`, optional) | `livekit:7880` |
| `https://api.example.com` (`API_DOMAIN`, optional) | `app:4000` (API-key integrations) |

Set `APP_URL=https://work.example.com` (and, with the bundled S3, `S3_ENDPOINT=https://files.example.com`).
Certificates, one of:

- **Let's Encrypt** (default): Caddy obtains one certificate per name above over ports 80/443 and renews it before
  it expires. Set `LETSENCRYPT_EMAIL` for expiry notices. Certificates live in the `caddydata` volume.
- **Your own certificate** (company CA, wildcard): add `tls /certs/fullchain.pem /certs/privkey.pem` to the site
  in `caddy/Caddyfile` and mount the files at `/certs` in the `caddy` service.
- **TLS ends in front of the server** (cloud load balancer, Cloudflare Tunnel): `TLS=off`, Caddy serves plain HTTP
  on port 80.

Only an IP address, no domain: `TLS=off ./install.sh --non-interactive --app-domain 203.0.113.10` serves plain
HTTP at `http://203.0.113.10` (`HTTP_PORT` for another port). Video, browser push, and installing as an app need
HTTPS; sign-in cookies lose the `Secure` flag, so keep such an installation on a
trusted network. Walk-through, and moving to another address later:
[Your own domain or IP](https://workspace.hungga1711.dev/docs/self-hosting/domain-and-https).

Ports: `HTTP_PORT`/`HTTPS_PORT` (default 80/443) are where people connect, through Caddy; `WEB_HOST_PORT`/`API_HOST_PORT`
(default 3000/4000) are the app's direct web and API ports on `BIND_ADDRESS`. When one of them already belongs to
another program, install.sh asks for another port (with `--non-interactive` it takes the next free one) and writes it
into `.env`. To choose up front: `curl -fsSL …/install.sh | HTTP_PORT=8080 WEB_HOST_PORT=3100 sh`, or set the variables in
`.env` and run `docker compose up -d`. A port other than 80 is part of the address (`http://localhost:8080`), and
Let's Encrypt needs 80 and 443 reachable from outside, so on another HTTP/HTTPS port use `TLS=off` behind your own
proxy, or your own certificate. The sites are in `caddy/Caddyfile`; `caddy/run.sh` turns the domain settings into
their addresses.

**Your own proxy on the host** (an existing nginx, a load balancer): `docker compose up -d --scale caddy=0`. The
app's ports are published on `BIND_ADDRESS` (default `127.0.0.1`): web `WEB_HOST_PORT` (3000), server `API_HOST_PORT` (4000), S3 8333, LiveKit 7880.
Route exactly as in the table. Host nginx example:

```nginx
map $http_upgrade $connection_upgrade { default upgrade; "" ""; }
server {
  listen 443 ssl; http2 on; server_name work.example.com;   # + ssl_certificate lines
  location /socket.io/ {
    proxy_pass http://127.0.0.1:4000; proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade; proxy_set_header Connection $connection_upgrade;
    proxy_set_header Host $http_host; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https; proxy_read_timeout 1h;
  }
  location ~ ^/(storage/|api/(mcp|docs)(/|$)) {   # local disk storage, MCP and API docs: the server
    proxy_pass http://127.0.0.1:4000;
    client_max_body_size 2g; proxy_request_buffering off; proxy_set_header Host $http_host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_set_header X-Forwarded-Proto https;
  }
  location / {
    proxy_pass http://127.0.0.1:3000; proxy_http_version 1.1;
    proxy_set_header Host $http_host; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;
  }
}
server {
  listen 443 ssl; http2 on; server_name files.example.com;  # + ssl_certificate lines
  client_max_body_size 2g; proxy_request_buffering off;
  location / { proxy_pass http://127.0.0.1:8333; proxy_set_header Host $http_host; }
}
```

Requirements for any proxy: WebSocket upgrade on `/socket.io/`, the original `Host` header kept for
the files domain (S3 signatures include it), `X-Forwarded-For`/`X-Forwarded-Proto` set, large request
bodies allowed on `/storage/` and the files domain. If more than one proxy sits in front of the web app, set
`TRUSTED_PROXY_HOPS`. The app must also reach `S3_ENDPOINT` (the bundled Caddy handles this with a network
alias; with a host proxy the public DNS name must resolve from inside containers).

**Your own S3 / Cloudflare R2** instead of local disk: set `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, keys, allow
CORS `PUT`/`GET` from `APP_URL` on the bucket, and leave `s3` out of `COMPOSE_PROFILES`.

## 6. Optional features

**AI.** Off by default. In Admin › AI the company switches on the assistant (then connects OpenAI, Claude, Gemini
or a self-hosted model there) and, separately, the recording of staff use of ChatGPT/Claude/Gemini/Copilot through
the browser extension. Nothing else to start: the ai module runs in the app's server. "Delete all AI Insights
data" in Admin › AI removes everything the extension recorded.

- **AI**: set `GEMINI_API_KEY`, `ANTHROPIC_API_KEY` or `OPENAI_API_KEY` (or `OPENAI_BASE_URL` for an
  OpenAI-compatible server such as Ollama; optionally `AI_*` routing, see `.env.example`), then
  `docker compose up -d app`. Without one everything else works and the AI features (the assistant, @AI,
  summaries, translation, task/doc AI) are hidden; the browser extension's ChatGPT/Claude tracking
  still works.
- **Video meetings** (LiveKit) are optional. Without `LIVEKIT_URL` the app shows no "Meet now", no call buttons
  and no meeting rooms (a shared `/meet/…` link explains that video is not set up); calendar meetings, agendas,
  minutes and action items work as usual. To enable them: set `LIVEKIT_URL=wss://meet.example.com`, `LIVEKIT_API_KEY`,
  `LIVEKIT_API_SECRET` (32+ chars), `MEET_DOMAIN=meet.example.com` with a DNS record, open TCP 7881 and
  UDP 50000–50100, then `docker compose --profile meet up -d` (Caddy adds the name's certificate).
  Users behind strict firewalls may need a TURN server (LiveKit docs: "TURN"). Recording (LiveKit
  Egress) is not part of this setup.
- **Leaving features out**: `DISABLED_FEATURES=whiteboards,calendar` in `.env`, then `docker compose up -d app`.
  The names are `docs` (documents and the file drive), `whiteboards`, `calendar` (calendar, events, meeting notes),
  `time` (attendance and leave) and `ai` (the assistant, AI Insights, agents and the AI section). A feature left out
  is gone from menus, pages and search, and its API answers 404; nothing is deleted, so removing the name and
  restarting brings it back with its data. Chat and tasks cannot be left out. An unknown name is ignored with a
  warning in the log.
- **Two-step sign-in**: each person turns it on in their profile; Admin › Sign-in & security can require it.
- **Desktop app** (macOS, Windows, Linux): there are no prebuilt downloads. On a computer with Rust, from a checkout,
  run `pnpm install && pnpm desktop:build <APP_URL>`; the app has this server's address built in, so staff
  never type it. Share the installers from `frontend/desktop/dist/` (a shared drive) and paste that link in
  Admin › Settings › Desktop app. Details: [frontend/desktop/README.md](../../frontend/desktop/README.md).
- **Web Push** (morning brief notifications): set the `VAPID_*` keys, then `docker compose build`
  (the public key is compiled into the web app) and `up -d`.

## 7. Backups

```bash
./backup.sh /var/backups/workspace      # database (pg_dump), files, .env and generated secrets
./restore.sh /var/backups/workspace/workspace-<date> --yes    # onto empty volumes
```

Nightly cron, retention, what is and is not in a backup, and how to test a restore:
[docs/runbooks/backup-restore.md](../../docs/runbooks/backup-restore.md).

## 8. Upgrades

```bash
./upgrade.sh 1.0.0      # backup, pull the tag, migrate, restart, health check; rolls back to the previous image on failure
```

Built from source: `./backup.sh && git pull && docker compose build && docker compose up -d`. Migrations are
forward-only and applied automatically (every start of `app`). Details and roll-back:
[docs/runbooks/upgrade.md](../../docs/runbooks/upgrade.md).

## 9. Operations

- Logs: `docker compose logs -f app` (JSON lines from the server, the web app's own lines in between).
- Status: `docker compose ps`; the server answers `/health` on port 4000 inside the network.
- Image commands: `docker compose exec app /app/infra/production/entrypoint.sh dlq list|show|replay …`,
  `docker compose run --rm --no-deps app migrate`, `docker run --rm workspace:local help`.
- Sign-in lives in the identity module: passwords (bcrypt), access tokens (Ed25519, rotated every 30 days),
  two-step codes. A locked-out owner: reset the password by e-mail ("Forgot password").
- Rotating secrets: what each one breaks and the order to change it in are in
  [the operations runbook §5](../../docs/runbooks/operations.md#5-rotating-secrets).
- One app container per installation: the server keeps events, caches and live connections in its own memory, so
  running two `app` replicas is not supported (ADR-0021).

## 10. Capacity

Measured on 2026-10-15 with [tooling/loadtest](../../tooling/loadtest/README.md), before the backend became one
process (ADR-0021; not yet re-run since): the whole stack (one replica each, telemetry off, TLS through the
proxy) inside one container limited to **2 CPU cores and
4 GB RAM** (Apple M3 cores; see "Other CPUs" below), k6 outside it. Each virtual user is a signed-in employee who
keeps the realtime socket open and every 30–60 s opens Home, lists their tasks, reads or posts in their team
channel (20 people), creates or updates a task, or searches. A step passes when, after the ramp, HTTP p95 < 500 ms,
< 1 % of actions fail, chat messages reach the other members' sockets in < 1 s (p95), and nothing restarts.

**Concurrent active users (2 CPU / 4 GB):**

| Workspace size | Online at once | Result | HTTP p95 | Chat delivery p95 | Box CPU (of 200 %) | Box RAM peak |
|---|---|---|---|---|---|---|
| 2,000 people | 250 | pass | 148 ms | 45 ms | 34 % | 1.0 GB |
| 2,000 people | 500 | pass | 148 ms | 54 ms | 46 % | 1.1 GB |
| 2,000 people | 1,000 | pass | 171 ms | 69 ms | 70 % | 1.4 GB |
| 6,000 people | 750 | pass | 335 ms | 98 ms | 77 % | 1.5 GB |
| 6,000 people | **875** | **pass** | 429 ms | 108 ms | 106 % | 1.6 GB |
| 6,000 people | 940 | fail | 1.5 s | 406 ms | 111 % | 1.7 GB |
| 6,000 people | 1,000 | fail | 629 ms | 203 ms | 115 % | 1.6 GB |
| 6,000 people | 1,250 / 1,500 | fail (Home p95 > 10 s) | | | 154–172 % | 1.8–2.4 GB |

So a 2 CPU / 4 GB server carries **about 875 people working at the same time** in a 6,000-person workspace, and
**at least 1,000** in a workspace of up to 2,000 people (the dataset size matters, see the bottleneck below).
Count on 70 % of that as the comfortable everyday figure.

**Realtime connections alone** (people with the app open, idle): **7,000 sockets pass** (box CPU 26 %, RAM 1.5 GB);
**10,500 were held** at 43 % CPU and 1.9 GB, where the test machine's own network path (Docker Desktop port
forwarding) stopped accepting more, not the server. About 25 KB per socket in the realtime code and 60 KB in the TLS proxy.

**Single actions, flat out** (4 users in a loop, no think time): my tasks 378 req/s, channel history 339, post a
message 202, search 91 (Postgres-bound), create a task 17, open Home 10 (p95 0.5 s). Signing in: 5–7 per second
(bcrypt cost 12, by design).

**What limited it** (found with `pg_stat_statements`; all three are fixed since, so the table above is
conservative):

1. Every app page loads the whole member directory: `/api/identity/members` is 1 MB for 6,000 people and Home's HTML
   1.25 MB; the query costs ~50 ms and the web server ~90 ms of CPU per Home view, on a single Node thread.
2. Creating a task finds the next board rank with `project_id IS NOT DISTINCT FROM $1` (no index use, ~135 ms on
   25k tasks) while holding the task-code counter row, so task creation is serialised at ~17 per second.
3. Home's project list counts every task of every project (~43 ms per view).

**Tuning that helped / did not:**

- The proxy's connection limit (nginx then, `worker_connections` 16384) capped one worker at ~8k sockets.
- Two web app replicas: about +10 % at 1,000 users. Not available with the one `app` container.
- Postgres `shared_buffers=512MB`, `effective_cache_size=2GB`, `work_mem=8MB`, `random_page_cost=1.1`: no measurable
  change (the costs above are CPU in queries, not I/O), so the defaults stay.

**Other CPUs.** `node tooling/loadtest/cpu-bench.mjs` (or inside the image, with bcrypt) measures one core; the
reference core gives bcrypt cost 12 = 200 ms, JSON stringify+parse of 1 MB = 3.8 ms. A typical cloud vCPU (one
hyperthread) is usually 1.3–1.7× slower than that (assumption; run the bench on your server and divide), so a
2 vCPU / 4 GB VPS should be expected to carry roughly **500–650** active people in a 6,000-person workspace and
**600–750** in a smaller one (measured before the fixes above).
